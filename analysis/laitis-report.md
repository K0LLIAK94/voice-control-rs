## Как Laitis получает звук

Основной путь установлен до границы Win32 API:

`4z..cctor → FG → NanoAudio.Wave.WaveInputs.WaveInEvent → winmm.dll waveInOpen / waveInStart → DataAvailable(byte[]) → HH → state machine → speech service → Sl.QG`

### Формат, буферы, микрофон

В глобальном конструкторе `4z..cctor`, token `0x06000b6d`, IL `00b5–00c5`, наблюдается создание `FG(16000,16,1,40,4)`.

| Параметр | Наблюдаемое значение |
|---|---|
| Частота | 16 000 Гц |
| PCM | little-endian, 16 бит |
| Каналы | 1, mono |
| Период буфера | 40 мс |
| Количество буферов устройства | 4 |
| Размер полного блока | 640 samples = 1 280 байт |
| Поток данных | 32 000 байт/сек |

`FG.Pf`, token `0x06000371`, file offset `384932`, присваивает `DeviceNumber`, `WaveFormat`, `NumberOfBuffers`, `BufferMilliseconds`, подписывает `DataAvailable` и `RecordingStopped`, затем вызывает `StartRecording`.

Обработчик `FG.GG`, token `0x06000374`, получает `WaveInBuffer.Data` и `BytesRecorded`, копирует только фактически заполненные байты через `FG.hG` (`0x06000375`) и отправляет массив подписчику. При остановке обработчики снимаются (`0x06000373`), освобождение выполняется отдельно.

Устройство выбирается по номеру WinMM. Для списка устройств и наблюдения за изменением default endpoint используются также `WaveIn.GetCapabilities`, `MMDeviceEnumerator` и `IMMNotificationClient`. Наличие CoreAudio API в списке ссылок **не означает**, что сам захват идёт через WASAPI.

### Доказательство WinMM

Ресурсная сборка статически восстановлена из зашифрованного поля RVA исходного EXE. Внутри неё находился `costura.nanoaudio.dll`. Его извлечённые байты:

`SHA-256 1633e58dadd7f4f4ed006358bf8de8ed59b48b77627c476b6831df51b055ec35`, 48 128 байт.

Второй запуск REA по этим конкретным извлечённым байтам показал:

- `WaveInEvent.OpenWaveInDevice`, NanoAudio token `0x060000af`, вызывает `WaveInterop.waveInOpenWindow`. Несмотря на внутреннее имя managed-метода, P/Invoke entry point — именно `winmm.dll!waveInOpen`, token `0x0600009b`.
- `StartRecording` (`0x060000b0`) вызывает `waveInStart` (`0x0600009f`) и создаёт worker через ThreadPool.
- `DoRecording` (`0x060000b2`) ждёт событие, обходит готовые `WaveInBuffer`, вызывает `DataAvailable` и возвращает буфер в очередь.
- В API также присутствуют `waveInPrepareHeader`, `waveInAddBuffer`, `waveInReset`, `waveInStop`, `waveInUnprepareHeader`, `waveInClose`.

Это позволяет воспроизвести получение PCM на Rust без запуска CLR и без копирования NanoAudio DLL в новое приложение.

## Как выделяется голосовая фраза

Координатор `HH` обновляет уровень звука на каждом входном блоке и передаёт блок текущему состоянию (`HH.OH`, token `0x06000403`). Состояния:

1. `4G`: ожидание голоса.
2. `tG`: подготовка, отсечение слишком короткого шума.
3. `WG`: запись подтверждённой фразы.

Названия `Waiting`, `Preparing`, `CancelledBecauseTooShort`, `Recording`, `CancelledBecauseOfLoudSound`, `StoppedBecauseTooLong`, `Stopped` дополнительно присутствуют в enum `Laitis.Secure.RecordingStatus`.

### Измеритель уровня: особенность оригинала

`HH.pH`, token `0x06000404`, file offset `394692`, не считает RMS и не берёт модуль PCM-sample. Он использует только старший байт каждого little-endian sample:

```text
peak = 0
for every pair of input bytes:
    quantized_sample = signed_i16(high_byte << 8)
    peak = max(peak, quantized_sample)
level = peak / 327.0
```

Следствия: отрицательная полуволна не увеличивает peak; младшие 8 бит отброшены; минимальная положительная ступень около `0.783`. Это наблюдаемая особенность кода Laitis, а не общая рекомендация для качественного VAD. При использовании другого измерителя в новой программе такое отличие нужно явно назвать.

### Профили чувствительности

Два массива констант были восстановлены **статически** из зашифрованной constant pool:

| Индекс | Требуемый рост относительно прошлого блока (`HH.WH`) | Минимальный уровень (`HH.xH`) |
|---|---:|---:|
| 0 | 0.5 | 0 |
| 1 | 2 | 1 |
| 2 | 3 | 4 |
| 3 | 5 | 6 |
| 4 | 15 | 10 |

`HH..cctor` (`0x06000408`) загружает массивы; `HH..ctor` (`0x06000407`) выбирает индекс **0**. Исходные значения: коэффициент адаптации `HH.tH=3`, previous level `HH.UH=1`, start level `HH.vH=-1`.

Увеличение/уменьшение профиля происходит через `HH.PH` (`0x06000405`) и `HH.qH` (`0x06000406`). Это дискретная адаптация, а не обучение нейросети.

### Ожидание (`4G.JF`, `0x0600038e`)

В обычном режиме, когда нет запрета из настроек и не работает подавление собственного озвучивания, начало требует одновременно:

`current_level > floor` и `current_level > previous_level + rise`.

Слишком громкий onset `current > (floor+rise)*3*2` увеличивает индекс порогового профиля. Начальный уровень фразы запоминается в `HH.vH` (`4G.AA`, `0x0600038f`).

До onset сохраняется кольцевой список последних блоков `PG`. Конструктор ожидания задаёт capacity 4. **Важная точность:** проверка в `PG.QG` (`0x0600037c`) использует `Count > capacity` до добавления. Поэтому список фактически может хранить 5 блоков, около **200 мс**, а не ровно 160 мс. Новый код может исправить это, но не должен называть исправление точной копией.

### Подготовка (`tG.JF`, `0x06000380`)

Подготовка получает накопленный pre-roll, добавляет новые блоки и считает **только новые** байты. Когда счётчик `>5333`, происходит переход в `WG`. При блоках по 1280 байт это 5 последующих блоков, то есть **200 мс** после onset.

Если уровень не превышает floor, счётчик тишины растёт на 40 мс. Когда он `>99`, кандидат отменяется как слишком короткий: на третьем тихом блоке, **120 мс**. Подготовка имеет собственный rolling buffer capacity 10 для возврата к ожиданию.

### Запись (`WG.JF`, `0x06000385`)

Запись сначала передаёт pre-roll и накопленные блоки recognizer-у (`WG.xG`, `0x06000384`), затем потоково подаёт новые 40-мс блоки.

Счётчик тишины увеличивается на 40 мс. В обычном режиме сбрасывается, если уровень не ниже запомненного onset либо снова выполнено условие `level>floor && level>previous+rise`. Когда счётчик `>500`, фраза завершается. При дискретных блоках фактическое окончание — **520 мс** тишины.

Лимит размера: `>320000` байт, около **10 сек** при 32 000 байт/сек. Он проверяется до добавления следующего блока; это не точный таймер 10 000 мс. Есть адаптация слишком долгих/громких фраз и отдельные пути отмены.

На завершении `WG.wf` (`0x06000386`) завершает запись/подачу recognizer-у и возвращается в `4G`, передав хвост pre-roll. `HH.vH` сбрасывается в `0.1`. На отмене используется отдельный путь `WG.TG` (`0x06000388`).

Дополнительно `5G.7G` (`0x06000399`) ослабляет порог после `>64000` байт, около двух секунд достаточно тихого звука при допустимом уровне выходного аудио. Режим собственного озвучивания и настройка подавления звука меняют некоторые ветки; цифры выше относятся к обычному режиму.

## Реальные движки распознавания

`HH.oH`, token `0x06000400`, выбирает реализацию по `EEA.fEA` (свойство `RecognitionService`). Значение по умолчанию задаётся в `EEA.Mo` (`0x06000ff9`) равным **0**.

| Значение | Ветка оригинала | Наблюдаемая реализация |
|---|---|---|
| 0 / default | `ih` | Google full-duplex, отдельные HTTP upload/download |
| 1 | `bg` | Yandex WebSocket speech service |
| 2 | `xF` | Windows `System.Speech.Recognition.SpeechRecognitionEngine` |
| 7 | `RF` → `IF` | Bing interactive recognition REST |

Это переключаемые backend-ы, а не собственная акустическая нейросеть, встроенная в EXE.

### Google: основной default-путь

Константы адресов восстановлены статически из локальных байтов:

- `mh.Nh` (`0x060003b8`): `POST https://www.google.com/speech-api/full-duplex/v1/up`.
- `mh.oh` (`0x060003b9`): `GET https://www.google.com/speech-api/full-duplex/v1/down`.
- Случайный paired session id создаётся в `mh.nh` (`0x060003b7`) и используется в обеих половинах.
- Content-Type строится как **`audio/l16; rate=16000;`**.
- Есть параметры language, `pFilter=0`, `maxAlternatives=1`, `app=chromium`, `continuous`, `interim`.
- В `ih.sF` / state machine `lh.MoveNext` (`0x060003b1`) создаются отдельные объекты отправки `rh` и приёма `Bh`; приём идёт параллельно загрузке.
- Текст отправляется на общий command router `Sl.QG` из `Bh.AC` / `Bh.ch` (`0x0600039c`, `0x0600039e`).

Адреса означают старый Chromium speech-api протокол. Анализ **не обращался** к этим endpoint-ам, не проверял актуальную доступность, не отправлял звук и не использовал встроенные реквизиты. Наличие строки в EXE не доказывает, что Google продолжает обслуживать этот протокол.

### Windows: локальный альтернативный путь

`xF.XF`, token `0x06000320`, file offset `377560`:

1. Берёт выбранный Windows recognition language через `CultureInfo.GetCultureInfo`.
2. Создаёт `SpeechRecognitionEngine` и загружает `DictationGrammar`.
3. Задаёт BabbleTimeout 1 час, EndSilenceTimeout 10 сек, InitialSilenceTimeout 10 сек.
4. `SetInputToAudioStream` получает PCM 16000 Гц, 16 бит, 1 канал, 32 000 байт/сек, block alignment 2.
5. Вызывает синхронный `Recognize()` и берёт `RecognizedPhrase.Text`.
6. Передаёт текст как окончательный результат в `Sl.QG` и освобождает engine/stream.

Большие timeout-ы здесь не заменяют внешний VAD: на вход этой ветке уже передаётся выделенная аудиофраза.

### Yandex и Bing

`IF..ctor` (`0x06000306`) формирует запрос к `https://speech.platform.bing.com/speech/recognition/interactive/cognitiveservices/v1`, POST, Content-Type `audio/wav; codec="audio/pcm"; samplerate=16000`, chunked body. Для части авторизации используются отдельные методы. Ветка `bg` использует Yandex: `zF` → state machine `0x0600032b` подключается к `wss://webasr.yandex.net/asrsocket.ws`. Init-сообщение указывает `audio/x-pcm;bit=16;rate=16000`, `lang=ru-RU`, `vad=false`, запрос промежуточных результатов и собственные серверные параметры. Здесь `vad=false` согласуется с выделением голосовой фразы внешним state machine Laitis. Встроенные авторизационные поля не воспроизводятся.

Ни значения ключей, ни заголовки с реквизитами не включены в этот отчёт. Новый проект должен использовать собственный поддерживаемый backend и собственные настройки авторизации, если облако вообще требуется.

## Как текст превращается в действие

Все изученные STT-ветки сходятся в `Sl.QG`, token `0x0600054a`. Объект `nl` содержит текст, признак final/interim, GUID результата и запись сеанса. Router различает промежуточные/окончательные результаты, запоминает `(GUID,text)` и не повторяет действие для той же окончательной пары.

Для клавиатурных действий подтверждён native boundary `user32.dll!SendInput`, Laitis token `0x06000875`. Его вызывает `Rt.tt` (`0x06000879`) для массива input records. Для строковой отправки существует отдельная ветка с `PostMessage` (`0x060011c2`); она не равнозначна глобальному нажатию Insert.

Для нового приложения из пользовательского запроса достаточно независимого явного dispatcher-а:

- `играй` → перейти в playing.
- `пауза` → перейти в paused.
- `мут` / `размут` → физическая последовательность Insert down/up для существующей привязки Discord, с защитой от повторов одного результата.

Insert является **переключателем** существующего Discord keybind. Само нажатие не сообщает приложению фактическое состояние Discord. Если состояние не проверяется отдельно, нельзя обещать достоверное принудительное «сейчас замучен» только на основе локального boolean.

## Что переносится в независимую реализацию на Rust

Наблюдаемое поведение, пригодное для самостоятельной реализации:

- Непрерывное получение PCM16 mono 16 kHz, логические блоки 40 мс, очередь с ограничением буферов.
- Pre-roll перед onset, состояния waiting/preparing/recording, минимальная длина кандидата, завершение по тишине, максимальная длина и адаптивные пороги.
- Разделение capture/VAD, speech backend и dispatcher-а.
- Исполнение только принятого окончательного результата, подавление повторного исполнения.
- Win32 `SendInput` для Insert.

**Осознанное отличие нового проекта:** локальный Vosk с отдельной русской моделью вместо старого внешнего Google endpoint-а. Vosk и его модель не обнаружены в исходном EXE. Это выбор реализации для работоспособного самостоятельного приложения, а не заявление, что Laitis использовал Vosk.

Точное совпадение микрофонного поведения требует либо WinMM waveIn*, либо отдельно доказанной эквивалентности выбранного capture backend-а. Если новая программа использует WASAPI/CPAL и ресэмплинг, она сохраняет формат и размер логических блоков, но не копирует низкоуровневый capture backend Laitis.

Новая реализация не должна включать Laitis.exe, извлечённые DLL, WPF-ресурсы, декомпилированный C#, чужие ключи, URLs с секретными query-параметрами или полные неочищенные evidence-файлы.

## Границы доказанного

- **Доказано статически:** identity исходного EXE, WinMM capture, PCM/буферы, VAD алгоритм и пороги, наличие и default выбор STT-веток, признаки Google full-duplex и Windows engine, граница SendInput.
- **Не проверялось динамически:** конкретный микрофон пользователя в Laitis, сеть/ответы старого Google/Bing, текущие сохранённые пользовательские настройки Laitis, исходная привязка Insert в Discord, все функции оригинального интерфейса.
- **Не восстановлено:** оригинальные имена/исходники автора, работа облачного акустического сервиса на стороне Google/Bing, полный код всех команд/плагинов.

Этот отчёт описывает исследованный загруженный артефакт и даёт проверяемую основу для независимого открытого кода. Он не выдаёт реконструкцию за оригинальный исходный код.


## Сопоставление с текущим Rust-кодом

На момент проверки в `src/winmm.rs` реализован именно WinMM capture с четырьмя собственными буферами 1280 байт и описанным выше PCM-форматом. `src/vad.rs` содержит восстановленные profile floor/rise, pre-roll, подготовку, окончание по тишине, предел длины и базовую дискретную адаптацию.

Преднамеренные отличия VAD от оригинала:

- Уровень считается по модулю **полного** PCM16 sample. Поэтому численное значение отличается от оригинального positive high-byte-only peak.
- Нет связанных с собственным TTS/выходной громкостью запретов на запись и снижение профиля: новое приложение само не синтезирует речь. Тихий вход может понизить профиль без проверки громкости выходного аудио.
- Предел длины срабатывает при достижении 160000 samples, а не после очередной проверки уже превышенного размера.
- Не воспроизведены дополнительные эвристики оригинала, меняющие onset factor/порог после пяти секунд непрерывной записи. Базовые повышения на громком onset/достижении предела и понижение после двух секунд тихого входа реализованы.

Это независимая реализация исследованного подхода, с явно указанными исправлениями и ограничениями, а не побайтовый перевод всех методов Laitis.
